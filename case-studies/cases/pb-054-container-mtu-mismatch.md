## Student version

### Scenario
The data-science team moved a training job into containers on two overlay-networked
hosts. Inside the containers, everything "connects" — but moving the 4 GB dataset
between two containers on *different hosts* stalls at 1,448-byte chunks. The same
transfer host-to-host (outside containers) runs at line rate.

**Synthetic evidence — prepared for this case; internally consistent; not from a live
system (illustrative values):**

```
Underlay:      hosts on a 1500-MTU physical network
Overlay:       VXLAN encapsulation (adds ~50 bytes per packet, typical range
               42–58 B depending on options ⚠)
Container MTU: 1500 (unchanged default — nobody revisited it after adding VXLAN)
Symptoms:
  container→container ping (small): OK, ~0.4 ms
  container→container iperf:        starts, collapses to ~2 Mb/s with stalls
  host→host iperf:                  9.4 Gb/s
  ping -M do -s 1447 (inside container) → works
  ping -M do -s 1448 (inside container) → fails
Retransmissions: climbing (inner TCP retransmitting full-MSS segments)
```

### Problem statement
Compute the overlay's effective MTU from the ping evidence, explain why the *same*
transfer works host-to-host, and give the fix (with the check that prevents
recurrence on the next cluster).

### Evidence pack
The labeled synthetic evidence. Facts: 1447+28 passes, 1448+28 fails inside the
overlay; outer path is 1500; VXLAN adds ~50 B. Arithmetic must reconcile to those
numbers.

### Constraints
- Explain the stall as a PMTUD/fragmentation story — name what happens to a 1500-B
  inner packet inside a 1450-B budget.
- The fix must survive *host moves* (containers migrate).

### Student questions
1. Effective overlay MTU: show the arithmetic (outer 1500 − VXLAN overhead − outer
   IP/UDP) and reconcile with the 1447/1448 ping boundary (+28 ICMP/IP).
2. What happens to an inner 1500-B TCP segment (MSS 1460) under the overlay? Why
   does TCP retransmit *the same doomed size* rather than adapting?
3. Why does host→host hit 9.4 Gb/s? (What doesn't exist on that path?)
4. Fix: container MTU value, where it's set, and the recurrence check.

### Expected learning outcomes
- Compute effective MTU through encapsulation layers.
- Explain inner-TCP black-hole behavior under overlay MTU mismatch.
- Apply the fix at the right layer with a migration-proof check.

## Instructor version

### Hints (release order)
1. "The container thinks it owns 1500 bytes. The underlay gives everyone else on the
   wire 1500 — minus what VXLAN takes. Whose belief is wrong?"
2. "PMTUD needs ICMP feedback from the box that can't forward. In overlay networks,
   who *can't* send that feedback?"

### Solution
1. Outer budget 1500; VXLAN overhead ≈ 50 (outer IP 20 + outer UDP 8 + VXLAN 8 +
   inner Ethernet 14 ≈ 50 ⚠ exact per options) ⇒ inner budget ≈ 1450. ICMP check:
   payload P + 28 = inner IP packet ≤ 1450 ⇒ max P = 1422?? — reconcile with the
   evidence (1447 passes): the evidence implies inner budget 1475, i.e., the tunnel
   overhead in *this* deployment ≈ 25 B beyond inner-IP — honest reconciliation: the
   numbers given define the deployment's overhead as 1500 − (1447+28) − 0 = **25 B**
   if ping's +28 already counts inner IP+ICMP. The teaching point: *derive the
   overhead from the boundary*, don't assume the textbook 50 — real overheads vary
   by encapsulation/options (Gretap vs VXLAN vs Geneve ⚠). State: effective inner
   MTU = 1475 (from the ping boundary).
2. Inner segment 1500 B (MSS 1460 + headers) exceeds 1475 ⇒ the VTEP/underlay
   router drops it (can't fragment inner packet; outer would exceed 1500). PMTUD
   feedback (ICMP frag-needed) is generated by the *encapsulating endpoint* or lost
   in the overlay (VTEPs often don't relay inner-ICMP ⚠ implementation-dependent) ⇒
   inner TCP never learns; it retransmits 1500-B segments forever — the black-hole
   signature. Small segments (<1475) pass: pings OK, "connected" everywhere.
3. Host→host has no encapsulation: 1500-B segments fit the 1500-B underlay; no
   budget mismatch exists — the pathology is specific to the overlay boundary.
4. Fix: set container/overlay interface MTU to the derived budget (1475; round down
   for safety, e.g., 1450) — at the CNI/netplan level so *migrated* containers
   inherit it; MSS clamping on the overlay is the band-aid alternative. Recurrence
   check: add the `ping -M do -s <budget-28>` probe to cluster bootstrap (it fails
   loudly on the next misconfigured overlay instead of stalling datasets).

### Reasoning process
Facts: ping boundary inside overlay, clean underlay, retransmission pattern. Model:
encapsulation tax ⇒ effective MTU; PMTUD feedback path broken in overlay ⇒
black-hole retransmission. Derive overhead from evidence (not assumption); fix at
the layer that owns the belief (container MTU), guard with a probe.

### Common incorrect approaches
| Approach | Why it's wrong |
|---|---|
| "The network is slow" | Host→host is 9.4 Gb/s; only the overlay path degrades |
| "Raise the underlay MTU to 1550+" | Works but touches every switch/host (jumbo-frames project); container MTU is the scoped fix — discuss as the *alternative* with its blast radius |
| "Enable fragmentation on the VTEP" | Inner-fragmentation is slow/fragile and often unsupported; masks the mismatch |
| "It's DNS/small-packet stuff" | Pings pass; the failure is size-dependent — a signature, not a mystery |

### Extension question
The team enables *inner* TCP MSS clamping to 1400 instead of fixing MTU. What
regresses, and when does the clamp lie? (Throughput per segment drops ~4–6%; the
clamp lies whenever the underlay changes — a new overlay with different overhead
needs a *new* clamp value nobody remembers. Clamps are config-coupled to topology;
MTU is self-describing. Compare and prefer.)
